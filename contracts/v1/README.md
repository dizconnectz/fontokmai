## 1. Data base URL และลำดับการโหลด
- ไฟล์ข้อมูลอยู่ใต้ `DATA_BASE_URL` ซึ่งเป็น config ของเว็บ และเปลี่ยน host ได้โดยไม่ rebuild
  - **ช่วงพัฒนา (ใช้งานได้แล้ว)**: `https://dizconnectz.github.io/fontokmai-data/data/v1/` อัปเดตจาก VPS ทุก 15 นาที (รอบ :03/:18/:33/:48) และ GitHub Pages อาจใช้เวลาอีก 1–3 นาทีหลังอัปโหลด
  - host นี้ส่ง `Access-Control-Allow-Origin: *` และ `Cache-Control: max-age=600` จึงต้องต่อท้าย `manifest.json?t=<เวลาปัจจุบัน>` เพื่อข้าม cache ของ CDN
  - ผู้ใช้เลือก GitHub Pages เป็น host (D28) · ถ้าย้ายไป Cloudflare Pages ภายหลัง ให้เปลี่ยนค่านี้อย่างเดียว
- ลำดับ:
  1. โหลด `manifest.json` แบบไม่ใช้ cache และตรวจ `schema_version === "1"`
  2. โหลดไฟล์ตาม `files[].path` (ต่อท้าย `?g=<generation_id>` เพื่อกัน cache เก่า)
  3. ตรวจว่า `generation_id` ในไฟล์ข้อมูลตรงกับ manifest (ยกเว้นไฟล์ใน `ref/` ซึ่งสร้างเป็นรอบของตัวเองและไม่มี `generation_id` ดูข้อ 8)
- ถ้าไม่ตรงกัน แปลว่าไฟล์ปนรุ่น:
  - โหลด manifest ใหม่ 1 ครั้ง
  - ถ้ายังไม่ตรง ให้แสดงชุดก่อนหน้าที่ครบพร้อมข้อความ “กำลังอัปเดต”
  - ห้ามรวมไฟล์ต่างรุ่น (ดู `examples/mixed-generation`)
- ตรวจ `sha256` กับ `size` เพิ่มเองได้ แต่ไม่บังคับ

## 2. ความสด ความครบ และสถานะแหล่ง
- **stale** เมื่อ `now > next_due_at + 15 นาที` โดยใช้นาฬิกาของเครื่องผู้ใช้ เพราะถ้าระบบหยุดทั้งชุด ไฟล์เก่าจะยังบอกว่าปกติ → แสดง “ข้อมูลไม่อัปเดต ตั้งแต่ …”
- **completeness**:
  - `complete` = ทุกแหล่งใน `source_status` เป็น `ok`
  - `partial` = มีบางแหล่งเป็น `degraded` หรือ `failed`
- **source_status[].status**:
  - `ok`
  - `degraded` = ดึงบางฉบับไม่ได้
  - `failed` = ดึงหน้ารวมไม่ได้ แต่ยังแสดงประกาศที่เก็บไว้แล้ว พร้อม `last_success_at` (ดู `examples/source-failed`)

## 3. เวลา null หน่วย และพิกัด
- เวลาเป็น ISO 8601 ที่มี offset เสมอ:
  - เวลาจาก CAP คง `+07:00` ตามต้นฉบับ
  - เวลาที่ระบบสร้าง (`generated_at`, `feed_generated_at`, `last_attempt_at`) เป็น UTC (`Z`)
  - แสดงผลเป็นเวลา `Asia/Bangkok` และห้ามเดา timezone เอง
- `null` = ต้นฉบับไม่มีค่า ไม่ได้แปลว่าศูนย์หรือ “ไม่มีภัย”
- `geometry` เป็น GeoJSON `MultiPolygon` ลำดับ `[longitude, latitude]` (WGS84) หรือ `null` · ประกาศของกรมอุตุฯ มี 16–164 polygon ต่อฉบับ
- `targets[]` เป็นรหัสจังหวัด ISO 3166-2 (เช่น `TH-10` = กรุงเทพมหานคร, `TH-13` = ปทุมธานี)

## 4. ประกาศ: message, event และ revision
- **event**: หนึ่งประกาศบนเว็บคือหนึ่ง event (`event_id` เช่น `tmd:TMD20260925071317_2`) ซึ่งรวม message ที่อ้างถึงกัน (Alert → Update → Cancel)
  - `source_message_id` = ฉบับล่าสุดที่ใช้แสดง
  - `supersedes` = ฉบับที่ฉบับนี้อ้างถึง
- **revision** ของ event เพิ่มเมื่อเนื้อหาที่แสดงเปลี่ยน รวมถึงเปลี่ยนสถานะ เช่น pending → active แต่ไม่เพิ่มเพียงเพราะดึงข้อมูลรอบใหม่
- **lifecycle_status**:
  - `pending` = ยังไม่ถึง `effective` แสดงล่วงหน้าได้พร้อมเวลาเริ่ม
  - `active` = มีผลอยู่ (`is_effective` เป็น true เฉพาะสถานะนี้)
  - `expired` และ `cancelled` อยู่ใน `tombstones` ไม่ใช่ประกาศที่มีผล
- **expires_policy**:
  - `source` = ใช้ `expires` ของต้นฉบับ
  - `default_24h` = 24 ชม. หลังเวลาที่ช้ากว่าระหว่าง `sent` กับ `effective` ใช้เมื่อต้นฉบับไม่มี `expires` หรือ `expires` ไม่ช้ากว่า `effective` โดย `qc_flags` บอกเหตุ (`missing_expires` หรือ `expires_not_after_effective`) → UI ควรบอกว่า “เวลาสิ้นสุดเป็นค่าประมาณ”
  - ข้อมูลจริงมีกรณีนี้แล้ว: TMD20260925163148_2 ระบุ `expires` 06:00 ก่อน `effective` 08:00
- ไฟล์มีเฉพาะฉบับ `status=Actual` และ `scope=Public` · ฉบับ Test/Exercise/System ไม่อยู่ในไฟล์
- เหตุที่ถูก Cancel แล้วจะไม่กลับเป็น active แม้ฉบับเก่ามาถึงทีหลัง (ดู `examples/out-of-order`)
- `notify_eligible` เป็น false ทั้งหมดใน P0/P1 เพราะยังไม่มีระบบแจ้งเตือน
- **เครดิต**: แสดง `credit_th` (“กรมอุตุนิยมวิทยา”) และลิงก์ `source_url` ทุกครั้ง พร้อมข้อความว่า fontokmai ไม่ได้เกี่ยวข้องหรือได้รับการสนับสนุนจากกรมอุตุนิยมวิทยา

## 5. feed_sequence, recovery_epoch และ cursor
- `feed_sequence` เพิ่มเมื่อ `alerts` หรือ `tombstones` เปลี่ยน ใช้เป็น cursor ให้ consumer ที่เก็บสถานะไว้ (เช่นแท็บที่เปิดค้าง) อัปเดตเมื่อค่าเพิ่ม
- `recovery_epoch` เปลี่ยนเมื่อระบบกู้สถานะที่เคยเผยแพร่ไม่ได้ (design 4.4 และ F1 ในรีวิว v6) → consumer ล้างสถานะที่เก็บไว้แล้วอ่าน feed ใหม่ทั้งชุด และไม่เทียบ `feed_sequence` ข้าม epoch
- `tombstones` มีเหตุที่จบภายใน 7 วันล่าสุด (`history_since`)
- `owner_epoch` ใน manifest เป็นหมายเลขผู้เผยแพร่ปัจจุบัน (เพิ่มเมื่อ takeover หรือ failback) ใช้ตรวจสอบย้อนหลัง consumer ไม่ต้องตัดสินใจจากค่านี้

## 6. ยังไม่รองรับใน slice นี้
- ยังไม่มีข้อมูลเหล่านี้ใน manifest: พยากรณ์, โซนเสี่ยงน้ำท่วม, สถานีฝนและระดับน้ำ, เขื่อน, CCTV และข่าว (ประวัติน้ำท่วมถนนมีแล้ว ดูข้อ 8)
  - UI ต้องแสดง “ยังไม่มีข้อมูล” ห้ามแสดงศูนย์หรือข้อมูลจำลองเหมือนข้อมูลจริง
  - ต้องรองรับไฟล์ใหม่ใน `files[]` ในอนาคตโดยไม่พัง

## 8. ประวัติน้ำท่วมถนน `ref/road_flood_history.json`
ตอบคำถาม “ถนนนี้เคยท่วมกี่ครั้ง” และ “ถนนแถวหมุดนี้เคยท่วมไหม” ในกรุงเทพฯ และปริมณฑล · ตัวอย่างอยู่ที่ `examples/road-flood-history/`

**ไฟล์และรอบอัปเดต**
- อยู่ใน `files[]` ของ manifest เมื่อมีไฟล์ที่ผ่าน schema · ไม่มีในบางรอบได้ ให้ UI แสดง “ยังไม่มีข้อมูล”
- สร้างใหม่สัปดาห์ละครั้ง (`built_at`) จึงไม่มี `generation_id` · โหลดด้วย `?r=<revision>` จาก manifest เพื่อข้าม cache เก่า และตรวจ `sha256` ได้ถ้าต้องการ
- ขนาดจริงราว 1–2 MB (GitHub Pages ส่งแบบบีบอัด) จึงควรโหลดเมื่อผู้ใช้เปิดส่วนนี้ ไม่ต้องโหลดตอนเปิดหน้าแรก

**ความหมาย**
- `sources[]`: ที่มาแต่ละแหล่ง ต้องแสดง `credit_th` คู่กับตัวเลขทุกครั้ง และลิงก์ `url` ไปหน้าชุดข้อมูล
  - `bma_road_flood_stats`: สถิติของสำนักการระบายน้ำ กทม. (CC BY) มีความลึก ความยาว เลนที่กระทบ และฝนรวม แต่ไม่มีพิกัด
  - `itic_longdo_events`: เหตุการณ์น้ำท่วมจาก iTIC/Longdo (CC BY 4.0) มีพิกัดและลิงก์รายเหตุการณ์ แต่ชื่อถนนอ่านจากหัวเรื่อง
- `roads[]` เรียงตาม `key` · `flood_days` = จำนวนวันที่มีรายงานอย่างน้อยหนึ่งครั้ง · `reports` = จำนวนรายงาน · `days_by_year` = วันต่อปี ค.ศ.
- `points` = พิกัด `[lon, lat]` ของรายงาน (เฉพาะที่มีพิกัด สูงสุด 30 จุด) · `recent` = รายงานล่าสุด 10 รายการ ใหม่สุดก่อน พร้อม `url` ถ้าต้นทางมีหน้ารายงาน
- **ต้องแสดง `notes_th` ใกล้ตัวเลขเสมอ** โดยเฉพาะ “ถนนที่ไม่มีรายงานไม่ได้แปลว่าไม่เคยท่วม”

**กติกาค้นชื่อถนน** (ต้องได้ผลตรงกับ `expected.json` ส่วน `normalize` และ `searches`)
1. แปลงคำค้นเป็น key:
   - Unicode NFC และเลขไทยเป็นเลขอารบิก
   - ลบ `*` และข้อความในวงเล็บ ยุบช่องว่าง แล้วตัด ` -–,.:;` ที่หัวท้าย
   - ตัด `ถนน`, `ถ.` หรือ `ถ ` ที่ขึ้นต้น และแปลง `ซ.` ที่ขึ้นต้นเป็น `ซอย`
   - ตัดหัวท้ายอีกครั้ง ลบช่องว่างและขีด (`-` `–` `—`) ทั้งหมด แล้วทำเป็นตัวพิมพ์เล็ก (แหล่งเขียนชื่อเดียวกันทั้งมีและไม่มีขีด เช่น รังสิต-นครนายก)
2. ถ้า key ว่าง (เช่นพิมพ์แค่ “ถนน”) ไม่ต้องค้น ให้แสดงคำแนะนำแทน
3. ผลคือถนนที่ `key` มีคำค้นอยู่ข้างใน เรียงตาม `flood_days` มากไปน้อย แล้ว `last_date` ใหม่ไปเก่า แล้ว `key`

| คำค้น | key |
|---|---|
| `ถนนสุขุมวิท` | `สุขุมวิท` |
| `ถ.พระราม 2` | `พระราม2` |
| `สุขุมวิท 21(อโศก)` | `สุขุมวิท21` |
| `ซ.เพชรเกษม 42 *` | `ซอยเพชรเกษม42` |
| `เฉลิมพระเกียรติ ร.๙` | `เฉลิมพระเกียรติร.9` |
| `ถ.รังสิต-นครนายก` | `รังสิตนครนายก` |
| `ถนน` | (ว่าง ไม่ต้องค้น) |

**กติกาถนนใกล้หมุด** (ต้องตรงกับ `expected.json` ส่วน `near`)
- ใช้ระยะ haversine (R = 6,371,008.8 ม.) จากหมุดไปยังจุดใน `points` ที่ใกล้ที่สุด แล้วเก็บถนนที่ไม่เกิน `radius_m` (ค่าตั้งต้น 2,000 ม.)
- เรียงตามระยะ (ปัดเป็นเมตร) ใกล้ไปไกล แล้ว `flood_days` มากไปน้อย แล้ว `key`
- ถนนที่มีแต่สถิติ กทม. ไม่มีพิกัด จึงหาด้วยระยะไม่ได้ ให้บอกผู้ใช้ว่าค้นด้วยชื่อถนนได้

**การแสดงผลที่แนะนำ**
- สรุปหนึ่งบรรทัด เช่น “ถ.สุขุมวิท เคยมีรายงานน้ำท่วม 7 วัน (2022–2025) ล่าสุด 10 พ.ค. 2025” พร้อมเครดิตแหล่ง
- กดดูต่อจึงแสดง `recent` (วันเวลา จุด ความลึก เลน ฝน และลิงก์ต้นทาง) และ `days_by_year`
- ใช้คำว่า “เคยมีรายงาน” ไม่ใช่ “ท่วมแน่” และห้ามแสดงเป็นการพยากรณ์

## 9. เรดาร์ฝน `radar.json` และภาพ `radar/*.png`
ภาพเรดาร์รวมทั้งประเทศของกรมอุตุฯ (ความเข้มฝนที่ระดับ 2 กม.) 4 ภาพล่าสุด (1 ชั่วโมง) อัปเดตทุก 15 นาที

- `radar.json` เป็นส่วนหนึ่งของ snapshot: มี `generation_id` ที่ต้องตรงกับ manifest แบบเดียวกับ `alerts.json`
- `frames[]` เรียงเก่าไปใหม่ ภาพล่าสุดคือตัวสุดท้าย · `time` เป็นเวลาถ่ายภาพ (UTC) ให้แสดงเป็นเวลาไทย · `path` อยู่ใต้ `DATA_BASE_URL`
- `coordinates` คือมุมภาพ [lon, lat] เรียง บนซ้าย → บนขวา → ล่างขวา → ล่างซ้าย ใช้กับ MapLibre image source ได้ตรงๆ
- `projection` = `EPSG:3857`: ภาพเป็น **Web Mercator** ระหว่างมุมทั้งสี่ คอลัมน์ห่างเท่ากันตามลองจิจูด แต่แถวห่างเท่ากันตาม Mercator y ไม่ใช่ละติจูด (เหมือนที่ MapLibre วาด image source และหน้าเรดาร์ของกรมอุตุฯ ก็วางภาพแบบเดียวกัน) · หลักฐาน: ภาพจริงขนาด 1800×2644 px ตรงกับความสูง Mercator ของกรอบนี้ (2644.4 px) ขณะที่กริดละติจูดเท่ากันจะสูง 2561.5 px · producer ปฏิเสธภาพที่สัดส่วนต่างเกิน 1%
- `legend[]` เรียงจากฝนแรงไปเบา (มม./ชม.) **อ่านจากแถบสีบนหน้าเว็บกรมอุตุฯ ทุกรอบ** (อ่านไม่ได้ใช้ชุดที่บันทึกไว้ 2026-09-28) · สีที่แถบเขียนซ้ำสองค่าใช้ค่าต่ำ · พิกเซลในภาพเป็นสี legend ที่ผสมพื้นขาวด้วยความทึบ `legend_opacity` (ชุดสีของ 28 ก.ย. = 1 คือสีตรงตัว ชุดเดิมคือ 0.816) · พิกเซลโปร่งใส = ไม่มีเสียงสะท้อนฝน
  - กรมอุตุฯ เปลี่ยนชุดสีเมื่อ 2026-09-28 ราว 11:40 น. · producer ตรวจทุกภาพ: ภาพเก่าที่ใช้สีชุดอื่นถูกตัดออก และถ้าภาพล่าสุดตรงกับแถบสีไม่ถึง 90% จะส่ง **`legend` ว่าง = ห้ามอ่านค่า** (เว็บยังแสดงภาพได้ แต่ไม่บอกความแรงฝน)
  - อ่านค่าที่หมุด: `x = (lon − west) / (east − west) × width` และ `y = (m(north) − m(lat)) / (m(north) − m(south)) × height` เมื่อ `m(lat) = ln(tan(π/4 + lat/2))` แล้วเทียบสีกับ `legend` หลังคิดความทึบ · ถ้าสัดส่วนภาพไม่ตรงกับความสูง Mercator (เกิน 1%) ห้ามอ่านค่า (ใช้ละติจูดแบบเส้นตรงจะคลาดราว 20 กม. แถว กทม.)
- ถ้าดึงภาพใหม่ไม่ได้ `source_status` ของ `tmd_radar` เป็น `failed` และ `frames` เป็นชุดเดิม → ถ้าภาพล่าสุดเก่ากว่า 45 นาทีให้ขึ้นป้าย “ภาพเรดาร์ไม่อัปเดต”
- ต้องแสดงเครดิต “กรมอุตุนิยมวิทยา”, เวลาภาพ และ `notes_th` (เรดาร์ไม่ใช่ปริมาณฝนที่วัดได้)

## 11. ชื่อพื้นที่ `ref/places.json`
ทะเบียนจังหวัด อำเภอ ตำบล พร้อมจุดละหนึ่งจุด สร้างจากจุดที่ตั้งตำบลของกรมการปกครอง (CC BY) ไฟล์ต้นทาง `pipeline/src/fontokmai/ref_data/places.json` เผยแพร่ทุกรอบ (ราว 1.6 MB, gzip ราว 170 KB) ตัวอย่างย่อสองจังหวัดอยู่ที่ `examples/places/places.json`

- `kind` = `province` | `district` | `subdistrict` · `code` 2/4/6 หลัก และรหัสแม่เป็น prefix ของรหัสลูก
- `name` ไม่มีคำนำหน้า (ต./อ./จ./แขวง/เขต) ใช้ค้น · `label` คือชื่อเต็มที่แสดง เช่น `ต.คลองหนึ่ง อ.คลองหลวง จ.ปทุมธานี` หรือ `แขวงบางนา เขตบางนา กรุงเทพมหานคร`
- `location` ของตำบลเป็น**จุดอ้างอิง ไม่ใช่ขอบเขต** ส่วนอำเภอและจังหวัดเป็นค่าเฉลี่ยของจุดตำบล ใช้ซูมแผนที่ไปหาเท่านั้น ห้ามใช้ตัดสินว่าจุดใดอยู่ในพื้นที่ใด
- โหลดเมื่อจำเป็น (เปิดช่องค้นหาหรือมีหมุด) และโหลดใหม่เมื่อ sha256 ใน manifest เปลี่ยน
- แสดงเครดิต `credit_th` ที่ช่องค้นหาและหน้าแหล่งข้อมูล

กติกาค้นของเว็บ (`apps/web/src/places.ts`):
1. แยกคำด้วยช่องว่าง ตัดคำนำหน้าที่คนพิมพ์ (`ตำบล`, `ต.`, `แขวง`, `อำเภอ`, `อ.`, `เขต`, `จังหวัด`, `จ.`) และแปลงชื่อย่อ `กทม`/`กทม.`/`กรุงเทพฯ` → กรุงเทพมหานคร, `โคราช` → นครราชสีมา
2. ทุกคำต้องอยู่ในชื่อของพื้นที่นั้นหรือชื่อพื้นที่แม่ และต้องมีอย่างน้อยหนึ่งคำอยู่ในชื่อของพื้นที่นั้นเอง (พิมพ์ `คลองหลวง` จึงไม่ได้ทุกตำบลในอำเภอ แต่ `คลองหนึ่ง คลองหลวง` ได้ ต.คลองหนึ่ง)
3. คะแนนเฉลี่ยต่อคำ: ตรงทั้งชื่อ 3, ขึ้นต้น 2, อยู่ในชื่อ 1, อยู่ในชื่อพื้นที่แม่ 0.5 · ลองต่อทุกคำเป็นคำเดียวด้วย (`บาง นา` → `บางนา`) · บวกจังหวัด 1.1 อำเภอ 0.5 เพราะชื่อที่ซ้ำกันมักหมายถึงพื้นที่ใหญ่ · เสมอกันเรียงจังหวัด → อำเภอ → ตำบล แล้วชื่อสั้นก่อน แล้วรหัส
4. เลือกแล้วปักหมุดที่ `location` ซูมให้เห็นทั้งพื้นที่ (กรอบของจุดตำบลในพื้นที่ + ขอบ) และจับคู่ประกาศทั้งแบบจุดอยู่ในขอบเขตประกาศ และแบบประกาศระบุชื่อจังหวัดนั้น (`area_desc_th`)
5. หมุดที่ปักเองบนแผนที่ตั้งชื่อว่า “แถว …” จากจุดตำบลที่ใกล้ที่สุดไม่เกิน 8 กม. เพราะเป็นจุด ไม่ใช่ขอบเขต

สถานที่อื่น (ห้าง โรงพยาบาล ฯลฯ) เว็บค้นจาก Photon (OpenStreetMap, © OpenStreetMap contributors) โดยเบราว์เซอร์ส่งเฉพาะคำที่พิมพ์ ไม่ได้อยู่ในไฟล์นี้

## 12. พยากรณ์ฝน `forecast/rain.json`
พยากรณ์ฝนจากแบบจำลอง (Open-Meteo, CC BY 4.0, ไม่ใช่ประกาศทางการ) บนตาข่ายจุด 0.25° ราว 900 จุดบนและรอบแผ่นดินไทย สร้างใหม่ทุก 6 ชั่วโมงแทนที่ไฟล์เดิม (ไม่เก็บย้อนหลัง) ตัวอย่าง 12 จุดรอบ กทม. อยู่ที่ `examples/forecast/rain.json`

- อยู่ใน manifest เหมือนไฟล์ `ref/` (sha256/revision) ไม่ผูกกับ `generation_id` · โหลดใหม่เมื่อ sha256 เปลี่ยน
- จุด `points[p] = [col, row]` อยู่ที่ `[lattice.west + col*step, lattice.south + row*step]`
- `hours[h]` คือเวลา**สิ้นสุด**ของฝนรวม 1 ชั่วโมง (เวลาไทย) เริ่มจากชั่วโมงที่กำลังเป็นอยู่ตอนดึง 72 ชั่วโมง · `rain[h][p]` หน่วย 0.1 มม. (`null` = ไม่มีค่า)
- `days[d]` วันตามปฏิทินไทย 7 วันเริ่มวันนี้ · `day_rain` (0.1 มม.), `day_probability` (โอกาสฝนสูงสุดของวัน %), `day_code` (WMO weather code)
- ค่าระหว่างจุดใช้ bilinear จากจุดรอบข้างที่มีค่า และไม่มีค่าเมื่อจุดตาข่ายที่ใกล้ที่สุดไม่มีข้อมูล (นอกประเทศ) 
- **สีบนแผนที่เป็นชุดของพยากรณ์เอง ไม่ใช่ `legend` ของเรดาร์ (ข้อ 9)**: วาดเป็นพื้นที่ซ้อนกันตามขั้นฝน มม./ชม. จากค่า bilinear ข้างบน ขั้นและสีคือ ≥0.5 `#cfe8fb` · ≥1 `#9fd0f5` · ≥2 `#5eaee9` · ≥4 `#2f86d8` · ≥8 `#2fb15a` · ≥16 `#f2c500` · ≥32 `#f76707` · ≥48 `#e03131` · ≥80 `#9c36b5` (ต้นทางคือ `FORECAST_LEVELS` ใน `apps/web/src/forecast.ts` และมีเทสต์ตรึงไว้)
- ฝนต่ำกว่า 0.5 มม./ชม. ไม่ระบายสี เพราะแบบจำลองกระจายฝนปรอยไปทั่ว **ไม่มีสีจึงไม่ได้แปลว่าไม่มีฝน** · คำอธิบายสีต้องเปลี่ยนตามโหมด: โหมดพยากรณ์ใช้ชุดนี้และบอกจุดเริ่ม 0.5 มม./ชม. โหมดสังเกตจริงใช้ `legend` ของเรดาร์
- ต้องติดป้าย “พยากรณ์” แยกจากเรดาร์ (สังเกตจริง) และประกาศทางการ แสดงเครดิต `credit_th` กับเวลา `fetched_at` และถ้าเก่ากว่า 12 ชั่วโมงให้ขึ้น “พยากรณ์ไม่อัปเดต”

- QC ก่อนเผยแพร่ (M54): ต้องระบุหน่วยฝน mm, โอกาสฝน %, เวลาไทย UTC+7; แกนชั่วโมง/วันต้องเรียงต่อเนื่องไม่ซ้ำ และจำนวนค่าในแต่ละชุดต้องตรงเวลา หากผิดไม่แทนที่ไฟล์เดิมหรือเปลี่ยนเวลาของชุดเดิม

## 14. ระดับน้ำคลอง กทม. `bkk/water.json`
ระดับน้ำล่าสุดของสถานีสูบน้ำ ประตูระบายน้ำ และจุดวัดในคลองของสำนักการระบายน้ำ กทม. ผ่าน DXS (อนุมัติให้เผยแพร่ต่อ 2026-09-26) ดึงทุกรอบ 15 นาที อยู่ใน manifest และมีสถานะแหล่ง `bma_dxs` · ตัวอย่างสังเคราะห์อยู่ที่ `examples/bkk/water.json`

- `stations[]` ทุกสถานีที่ DXS ให้ เรียงตาม `code` · `name_th` ตามต้นทาง (ส. = สถานีสูบน้ำ, ปตร. = ประตูระบายน้ำ, ค. = คลอง) · `location` = `[lon, lat]` หรือ null เมื่อต้นทางไม่มีหรืออยู่นอกกรอบ กทม. (กันพิกัดสลับ)
- `level_in_m` / `level_out_m` = ระดับน้ำด้านใน/ด้านนอกของสถานี หน่วย **เมตรเทียบระดับทะเลปานกลาง (ม.รทก.)** ไม่ใช่ความลึกน้ำท่วมบนถนน ต้องบอกผู้ใช้เสมอ · ค่าที่เป็นไปไม่ได้ (นอก ±10 ม. เช่น -999) เป็น null
- `observed_at` คือเวลาวัด (เวลาไทย) แยกจาก `fetched_at` ที่เราดึง · สถานีที่ไม่มีค่าล่าสุดยังอยู่ในรายการโดยค่าเป็น null และต้องแสดงว่า “ไม่มีค่าล่าสุด” ไม่ใช่ปกติ
- เครดิต `credit_th` เป็นข้อความ ห้ามใช้โลโก้ของสำนักการระบายน้ำ และลิงก์ออกไป `source_url` (หน้าสาธารณะ) เท่านั้น ห้ามลิงก์เข้า DXS
- เมื่อดึงไม่ได้ producer เผยแพร่ไฟล์เดิมต่อ (สถานะ `bma_dxs` เป็น degraded/failed) เว็บจึงต้องดูอายุจาก `fetched_at` และ `observed_at`
- **ดึงเป็นครั้งๆ (ใช้อยู่ตอนนี้)**: DXS ตอบเฉพาะเครื่องที่อยู่ในไทย VPS จึงไม่เรียกเอง ไฟล์ข้อ 14–16 มาจากการสั่ง `bkk-fetch` บนเครื่องในไทยเป็นครั้งๆ แล้วคัดลอกไปที่ VPS · รอบของ VPS ใส่ไฟล์ที่ผ่านสัญญาใน manifest ได้ไม่เกิน 30 วันหลัง `fetched_at` และ **ไม่มีสถานะแหล่ง `bma_dxs`** ผู้ใช้ข้อมูลต้องดูอายุจาก `fetched_at` เท่านั้น · เว็บต้องบอกว่า “ไม่ได้อัปเดตอัตโนมัติ” เมื่อเก่ากว่า 45 นาที, ขึ้น “ข้อมูลนี้ไม่ใช่ข้อมูลเรียลไทม์ · ข้อมูล ณ วันที่ …” เมื่อเก่ากว่า 1 วัน และห้ามแสดงรายงานถนน (ข้อ 16) ของวันอื่นเป็นสถานการณ์วันนี้ (พับไว้พร้อมวันที่ได้)

- `pumps_running` (เพิ่ม 2026-09-28 ไม่บังคับ): จำนวนเครื่องสูบที่เดินอยู่ตอนวัด จาก `pumpdata` ของ `GetWaterLastData` · `null` = สถานีไม่ได้บอกสถานะ (ไม่ใช่ “หยุดทุกเครื่อง”) · เป็นจำนวนเครื่อง ไม่ใช่กำลังระบายน้ำ
- `previous_level_in_m` / `previous_observed_at` (เพิ่ม 2026-10-03 ไม่บังคับ): ระดับด้านในของค่าวัดก่อนหน้าตามไฟล์ที่เว็บเผยแพร่อยู่ตอน `bkk-fetch` (ไม่เกิน 24 ชม. ก่อน `observed_at`) ใช้บอกว่าน้ำขึ้นหรือลง · ส่งค่าวัดเดิมซ้ำ (เวลาวัดเท่าเดิม) คงการเทียบครั้งแรก · `null` = ไม่มีค่าก่อนหน้าให้เทียบ · **เป็นการเทียบของเว็บนี้เอง ไม่ใช่ของสำนักการระบายน้ำ** และไม่ได้บอกว่าใกล้ล้นตลิ่งหรือไม่ เพราะ DXS ไม่มีระดับตลิ่งหรือเกณฑ์วิกฤต (ข้อ 14.1) เว็บต้องบอกผู้ใช้ว่า “บอกไม่ได้ว่าวิกฤตหรือยัง” พร้อมลิงก์ที่มา ซึ่งเป็นหน้าของ กทม. ที่แสดงเกณฑ์

### 14.1 หลักฐานระดับน้ำเทียบตลิ่ง (เพิ่ม 2026-09-30, ยังไม่มีแหล่งสด)
- `bank_observations` เป็น optional ค่าเริ่มต้น `[]` ไฟล์เก่ายังใช้ได้ · DXS ปัจจุบันไม่ให้ข้อมูลตลิ่ง จึงต้องคงว่าง ไม่ใช้ระดับทะเล 0 ม. หรือ GloFAS แทนตลิ่ง และไม่สร้างค่าทดสอบในข้อมูลจริง
- แต่ละรายการมี `id`, `name_th`, `observed_at`, `verified`, `source_url`, `credit_th`; เวลาต้องเป็นเวลาวัด/รายงาน ไม่ใช้เวลาดึง `verified` หมายถึง producer ตรวจคุณภาพและขอบเขตหลักฐานแล้ว ต้องลงทะเบียนสิทธิ์แหล่งและตรวจ coverage ก่อนเปิดใช้
- `kind: measurement`: `geometry` เป็น Point เท่านั้น; `level_m`, `bank_m` เป็นเมตรหรือ null, `level_datum`/`bank_datum` และ `level_side`/`bank_side` ต้องระบุและตรงกัน จึงคำนวณระดับน้ำลบตลิ่งได้ · ผลเฉพาะจุดติดป้ายทดลอง ไม่ขยายเป็นเส้น/พื้นที่ · เกินเป็นแดง เท่ากันเป็นส้ม ต่ำกว่าเป็นฟ้า (ไม่ได้แปลว่าปลอดภัย)
- `kind: reported_reach`: `geometry` เป็น LineString อย่างน้อย 2 พิกัดของช่วงที่ต้นทางยืนยันจริง; `status` คือ `above_bank`, `at_bank`, `below_bank`, `unknown` ตามรายงานต้นทางสำหรับช่วงนั้น ห้ามนำสถานีจุดเดียวหรือ buffer 3 กม. มาอ้างทั้งช่วง
- พิกัด WGS84 `[lon,lat]` มีช่วงตัวเลขถูกต้อง · ทุกชนิดเมื่อ `verified=false`, ไม่มีเวลา, เวลาอนาคต หรืออายุเกิน 60 นาทีเป็นเทา/ยังยืนยันไม่ได้ รวมทั้งการเทียบระดับที่ไม่มีค่าหรือ datum/ฝั่งไม่ตรงกัน · เวลาดึงซ้ำไม่ทำให้สถานะสดใหม่
- Consumer มีจุด/เส้นและ popup พร้อมแหล่ง/เวลา, รายการที่กดด้วยคีย์บอร์ดได้, คำกำกับสี และซ่อนชั้นนี้เมื่อเลื่อนไปพยากรณ์ · ถ้าไม่มีรายการไม่แสดงการ์ดว่าง · ไม่ใช่ขอบเขตพื้นที่ท่วม/ความลึกบนถนน/ประกาศเตือนภัย

- `gauges[]` เรียงตาม `code` · ฝนสะสม `rain_15min_mm`, `rain_1h_mm`, `rain_3h_mm`, `rain_24h_mm` (มม.) ถึง `observed_at` · null = ไม่มีค่า (ไม่ใช่ 0)
- เป็นค่าตรวจวัดที่จุดเดียว ต่างจากเรดาร์ (ข้อ 9) ที่เป็นค่าประมาณจากภาพ และจากพยากรณ์ (ข้อ 12) ต้องติดป้าย “วัดจริง” และเวลาวัด

## 16. น้ำท่วมขังถนนสายหลัก กทม. รายวัน `bkk/flooding.json`
รายงานของเจ้าหน้าที่สำนักการระบายน้ำ (`getFloodingDailyReport`) ของวันนี้ตามเวลาไทย ดึงในรอบเดียวกับข้อ 14 · ตัวอย่างสังเคราะห์อยู่ที่ `examples/bkk/flooding.json`

- `reports[]` เรียงถนนที่ยังท่วมก่อน แล้วเริ่มท่วมล่าสุดก่อน · `dry_at` = null แปลว่ายังไม่แห้ง (ต้นทางเขียนเวลาแห้งเป็น 00:00) · `flood_start` อาจเป็นเมื่อคืนก่อน
- `depth_cm` = ความสูงน้ำบนผิวถนนสูงสุดที่รายงาน (ซม.) · `length_m` · `lanes_th` (เช่น 1-2 เลน, เต็มผิว) · `rain_mm` ฝนรวมที่รายงาน
- **ไม่มีพิกัด**: ต้นทางให้เพียงเขต ถนน และบริเวณ เว็บจึงต้องไม่ปักหมุดเหมือนรู้ตำแหน่ง แสดงเป็นรายการ และจับคู่กับถนนใกล้หมุดได้เฉพาะด้วยชื่อถนนพร้อมบอกว่าเป็นการจับคู่ชื่อ
- เป็นรายงานเฉพาะถนนสายหลักที่เจ้าหน้าที่ติดตาม ถนนที่ไม่มีในรายงานไม่ได้แปลว่าไม่ท่วม · producer ปฏิเสธคำตอบที่เป็นของวันอื่น และเก็บไฟล์เดิมเมื่อดึงไม่ได้ (เหมือนข้อ 14)

## 18. เขื่อนใหญ่ `water/dams.json`
ปริมาณน้ำรายวันของเขื่อนใหญ่ทั่วประเทศ (กรมชลประทานและ กฟผ.) จาก `GetDam` ผ่าน DXS · ตัวอย่างอยู่ที่ `examples/bkk/dams.json`

- `volume_mcm` ปริมาณน้ำวันที่รายงาน, `storage_mcm` ความจุที่ระดับเก็บกัก, `percent` = ร้อยละของความจุ, `inflow_mcm`/`outflow_mcm` น้ำไหลเข้าและระบายของวัน (ล้าน ลบ.ม.) · null = ไม่มีค่า
- `location` มาจาก OpenStreetMap (ODbL) ตามตาราง `pipeline/src/fontokmai/ref_data/dam_locations.json` · `location_kind` = `dam` (สันเขื่อน) หรือ `reservoir` (กลางอ่าง เมื่อหาสันเขื่อนไม่พบ) · เขื่อนที่หาตำแหน่งไม่พบมี `location` เป็น null ต้องแสดงเป็นรายการ ไม่ปักหมุดเดา
- น้ำมากกว่าร้อยละ 80 แปลว่าเหลือที่รับน้ำน้อย ไม่ใช่การพยากรณ์ว่าท้ายเขื่อนจะท่วม
- **ตัวเลขล่าสุดที่มี (เพิ่ม 2026-10-01, ไม่บังคับ)**: เขื่อนที่รายงานของวันไม่มีทั้ง `percent`, `volume_mcm`, `inflow_mcm` และ `outflow_mcm` มี `dams[].last_known` = ตัวเลขชุดล่าสุดจากรายงานก่อนหน้าที่เว็บเผยแพร่ พร้อม `report_date` และ `fetched_at` ของชุดนั้น (ไม่เกิน 7 วัน, ดึงซ้ำยังคงวันเดิม) · ฟิลด์ของวันยังว่างตามจริง ผู้ใช้ต้องแสดงพร้อมวันที่และเวลา ห้ามแสดงเหมือนเป็นของวันนี้ · การ์ดสรุปใช้ได้เมื่อวันที่ของชุดนั้นไม่เกิน 1 วัน (M26) และบอกวันในข้อความ · ที่มา: 1 ต.ค. 2569 รายงานมีตัวเลขแค่ 10 จาก 35 เขื่อนถึงบ่าย
- **อัปเดตอัตโนมัติ (เพิ่ม 2026-10-02, ไม่บังคับ)**: `automatic` = `true` เมื่อเซิร์ฟเวอร์ดึงเองทุก 2 ชั่วโมงจาก API เขื่อนใหญ่ของกรมชลประทาน (`app.rid.go.th/reservoir/api/dam/public` ข้อมูลเปิด data.go.th `big_dams_public` CC BY ตัวเลขชุดเดียวกับที่ DXS ส่งต่อ ตรวจ 35/35 ตรงกัน) · เปรียบเทียบการระบายกับวันก่อนหน้าล่าสุดในประวัติของกรมฯ ที่มีตัวเลขเกินครึ่ง (ไม่เกิน 3 วัน) และเขื่อนที่ว่างใช้ตัวเลขล่าสุดในประวัติไม่เกิน 7 วัน · เว็บถือว่าไฟล์ `automatic` ล่าช้าเมื่อเกิน 6 ชม. - **ระบายเทียบรายงานก่อนหน้า (เพิ่ม 2026-09-29, ไม่บังคับ)**: `previous_report_date` = วันของรายงานที่ใช้เทียบ และ `dams[].previous_outflow_mcm` = ระบายของวันนั้น · `GetDam` ไม่รับวันที่ (ให้แค่รายงานล่าสุด) ตัวดึงจึงเทียบกับไฟล์ที่เว็บเผยแพร่อยู่ก่อนดึง: รายงานก่อนหน้าต้องเก่ากว่าไม่เกิน 3 วัน ดึงซ้ำในวันรายงานเดียวกันใช้การเทียบเดิม ไม่มีก็เป็น null (ไฟล์เก่าไม่มีสอง field นี้) · **ระบายเพิ่มมาก** (เกณฑ์ทดลองของเว็บ ไม่ใช่เกณฑ์ของกรมชลประทาน): เพิ่มอย่างน้อย 1 ล้าน ลบ.ม./วัน และอย่างน้อย 1.5 เท่า (`bma_dxs.release_up` ต้องตรงกับ `releaseChange` ของเว็บ) · การเทียบถี่ได้เท่าที่ผู้ใช้กดอัปเดต กทม. ## 20. แนวโน้มน้ำในแม่น้ำ `forecast/rivers.json`
อัตราการไหลรายวันจากแบบจำลอง GloFAS ของ Copernicus Emergency Management Service ผ่าน Open-Meteo Flood API (CC BY 4.0) ที่จุดบนแม่น้ำสายหลัก 14 จุด (`pipeline/src/fontokmai/ref_data/river_points.json`) ย้อนหลัง 7 วัน วันที่ดึง และอีก 29 วันข้างหน้า (`forecast_days=30` นับวันที่ดึงด้วย รวม 37 วัน) สร้างใหม่วันละครั้งแทนที่ไฟล์เดิม ใช้งบเรียก Open-Meteo ก้อนเดียวกับข้อ 12 · ตัวอย่างอยู่ที่ `examples/forecast/rivers.json`

- อยู่ใน manifest เหมือนไฟล์ `ref/` (sha256/revision) ไม่ผูกกับ `generation_id`
- `days[d]` วันตามปฏิทินไทย เก่าสุดก่อน · ทุกชุดของแต่ละจุด (`discharge` ของรอบควบคุม, `median`, `p25`, `p75` ของชุดพยากรณ์) มีค่าหนึ่งค่าต่อวัน หน่วย ม³/วินาที (`null` = ไม่มีค่า)
- `location` คือพิกัดที่ขอจากแบบจำลอง เลือกครั้งเดียวให้ช่องตาข่าย 0.05° อยู่บนลำน้ำหลัก ไม่ใช่ตำแหน่งสถานีวัดน้ำ
- **เป็นค่าแบบจำลอง ไม่ใช่ค่าวัดจริงและไม่ใช่ประกาศ** ค่าอาจต่างจากปริมาณน้ำที่วัดได้มาก (เช่น เจ้าพระยาที่กรุงเทพฯ) เว็บจึงแสดงเฉพาะแนวโน้มเทียบกับวันนี้ ไม่แสดงตัวเลข ม³/วินาที เป็นระดับน้ำ และต้องบอกว่าเป็นแบบจำลองทุกที่ที่แสดง
- แนวโน้มที่เว็บคำนวณ (ทดลอง ไม่ใช่เกณฑ์ของหน่วยงาน): ค่ามัธยฐานสูงสุดใน 7 วันข้างหน้าเทียบค่าวันนี้ ≥ +30% “เพิ่มขึ้นมาก”, ≥ +10% “เพิ่มขึ้น”, ต่ำสุด ≤ −10% “ลดลง” (รวมค่าที่ขอบพอดี), นอกนั้น “ทรงตัว” · ต้องมีค่าครบทั้ง 7 วัน ไม่เช่นนั้น “ยังบอกแนวโน้มไม่ได้” · ถ้าเก่ากว่า 36 ชั่วโมงให้ขึ้น “พยากรณ์ไม่อัปเดต” และ popup ที่เปิดอยู่ต้องเปลี่ยนตามเวลา · ป้ายปลายกราฟใช้วันจริงของไฟล์ (ปกติ −7 ถึง +29 วัน)

- `points[].kind` (เพิ่ม 2026-10-02 ไม่บังคับ ค่าเริ่ม `station`): `station` = จุดที่เลือกเอง (14 จุด) เป็นหมุดบนแผนที่และอยู่ในรายการ “เตรียมรับมือ” · `reach` = จุดราวทุก 50 กม. ระหว่างนั้น (`ref_data/river_reaches.json`) ใช้ระบายสีช่วงแม่น้ำตามข้อ 23 เท่านั้น ไม่เป็นหมุดและไม่เข้ารายการสรุป

- QC ก่อนเผยแพร่ (M54): หน่วยทุกชุดต้องเป็น m³/s และ UTC+7; วันเรียงต่อเนื่องไม่ซ้ำ; p25 ≤ median ≤ p75 ในค่าที่มี ถ้าผิดเก็บไฟล์เดิมพร้อมเวลาเดิมและ log ข้อผิดพลาด

## 29. พื้นที่น้ำท่วมซ้ำซาก `ref/flood_freq.json`
สถิติพื้นที่ที่ GISTDA เคยแปลว่าน้ำท่วมจากภาพดาวเทียมในอดีต สรุปรายตำบลของจังหวัดใน `provinces` (ค่าตั้งต้น 10–14; `--provinces all` = ทั้ง 77 จังหวัด) สร้างด้วยมือด้วย `fontokmai flood-freq` บน VPS (ต้องมี key) เขียนไฟล์หลังจบแต่ละจังหวัด สั่งซ้ำจะข้ามจังหวัดที่มีแล้ว (`--again` อ่านใหม่) แล้วรอบปกติเผยแพร่ต่อ (เพิ่ม 2026-10-04) · ทั้งประเทศราว 7.8 ล้านรายการ ดาวน์โหลดราว 27 GB ครั้งเดียว ไม่เขียนข้อมูลดิบลงดิสก์ ไฟล์ผลราว 1 MB เว็บโหลดเมื่อปักหมุดครั้งแรก
- `subdistricts[]`: `code` (รหัสตำบล DOPA 6 หลัก), `name_th`, `area_rai` (พื้นที่ที่เคยท่วมอย่างน้อยหนึ่งครั้ง), `max_freq` (ส่วนที่ท่วมบ่อยสุดกี่ครั้ง), `rai_by_freq[k]` (ไร่ที่ท่วม k+1 ครั้งพอดี)
- `data_created` วันที่ GISTDA สร้างข้อมูล (2025-06-17 ตอนอ่าน) · ไม่ใช่การพยากรณ์ และตำบลที่ไม่มีในรายการไม่ได้แปลว่าไม่เคยท่วม · จังหวัดที่ไม่อยู่ใน `provinces` เว็บไม่พูดอะไรเลย
- เว็บแสดงในการ์ดหมุดของตำบลนั้นเป็นข้อมูลระดับตำบล ไม่ได้บอกว่าจุดที่ปักท่วม
