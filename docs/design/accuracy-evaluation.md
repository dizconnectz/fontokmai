## 2. ข้อมูลที่ขอให้ Claude เก็บ

เก็บแบบเพิ่มรุ่นใหม่ ไม่เขียนทับ รุ่นเปลี่ยนจึงเก็บเนื้อหาใหม่และใช้ hash อ้างซ้ำ จำกัดเฉพาะพื้นที่/จุดนำร่องก่อน:

1. **ทุกครั้งที่เผยแพร่**: `generation_id`, เวลา scheduled/start/published, commit, rules/schema version, hash ของไฟล์ที่ใช้, รายการ summary พร้อมเหตุผลทั้งหมด/คะแนน/ขอบเขต/วันเป้าหมาย รวมรายการที่ถูกตัดจากเพดาน 40, coverage และสาเหตุที่ไม่ประเมิน เวลาที่ input แต่ละชุดมาถึงจริงและเวลาสังเกตต้องแยกกัน
2. **ทุกรุ่นพยากรณ์ที่เปลี่ยน**: ผู้ให้บริการ/model, model run/init ถ้าต้นทางให้ (ไม่เดา), fetched/first-seen/published, เซลล์และสถานีที่เลือกพร้อมวิธีจับคู่, ค่า null/หน่วย, ช่วงสะสมเริ่ม–จบจริงของชั่วโมงและวัน, สมาชิกโมเดล/ค่ากลางถ้ามี วันไทยกับรอบ 07:00 ของสถานีต้องไม่ปนกัน ถ้า API ย้อนหลังคืนผลที่แก้แล้ว ใช้แทนพยากรณ์ที่เคยเผยแพร่ไม่ได้
3. **ค่าฝน/น้ำวัดจริงที่ได้รับแต่ละครั้ง**: station id, observed/fetched/first-seen, period start/end, หน่วย/ฐานระดับ, ค่า, QC, coverage/gap, รุ่นแก้ไข; เก็บ null ให้ต่างจากศูนย์ DXS ดึงเป็นครั้งๆ จึงอาจตรวจความแม่นไม่ได้หลายช่วง ห้ามเติมช่องว่างจากการอ่านสะสม 24 ชม. ซ้ำหรือบวกหน้าต่างที่ซ้อนกัน
4. **เหตุการณ์น้ำท่วม**: id ต้นทางและ id เหตุการณ์ที่รวมรายการซ้ำ, เกิด–สิ้นสุด/first-seen/แก้ไข/ปิด, พิกัดหรือขอบเขตและความแน่นอน, แหล่ง/สถานะยืนยัน, หลักฐานแห้งเมื่อมีข้อมูลจริง รายงานหายจากฟีด/หมด 12 ชม. ไม่ได้แปลว่าน้ำแห้ง เก็บเฉพาะข้อเท็จจริงตามสิทธิ์ ไม่เก็บข้อมูลระบุตัวผู้แจ้งเพิ่ม
5. **ทะเบียนและงบ**: รุ่นพิกัด/ขอบเขตสถานี–พื้นที่และ datum, license/attribution/ระยะเก็บที่อนุญาต, จำนวนแถว/bytes ต่อวันจริง, ขนาดก่อน–หลังบีบอัด, retention job และหลักฐาน restore สำเร็จ รวมสถานะ source หาย/รอบพลาดเพื่อไม่เลือกเฉพาะวันที่ระบบทำงานดี

ข้อเสนอเริ่มเก็บ 90 วันแบบจำกัดขนาดตามที่วัดได้จริงและสิทธิ์แต่ละแหล่ง (ไม่แทน retention DXS ที่ตกลงแล้ว) เก็บคู่ประเมิน/ผลรวมระยะยาวได้เมื่อสิทธิ์รองรับ ไม่เพิ่มภาพเรดาร์เต็มทุก 15 นาทีหรือ JSON ทั่วประเทศเพียงเพื่อแผนนี้; ผลรายอำเภอ/ตัวอย่างพิกเซลที่ใช้ + hash/legend/version ใช้ตรวจเบื้องต้นได้ แต่ **ไม่พอ replay กฎอ่านภาพรุ่นใหม่** ถ้าไม่มีภาพต้นฉบับ ต้องระบุข้อจำกัดนี้

## 3. วิธีจับคู่และป้องกันผลดูดีเกินจริง

- ตรึงตารางสถานีและระยะจับคู่ก่อนเห็นผล; ค่าพยากรณ์ที่จุดไม่ใช่ค่าเฉลี่ยอำเภอ ใช้ขอบเขตพื้นที่ที่ตรวจได้กับรายงาน ไม่ยืนยันอำเภอจาก “ตำบลที่จุดกลางใกล้ที่สุด” เงียบๆ ตรวจแนวชายแดนอำเภอด้วยตนเองและติดป้ายตำแหน่งไม่แน่นอน
- ฝน: ตรวจหน้าต่างชั่วโมง/24 ชม. ให้ตรงกัน ไม่เอาฝนวันปฏิทินเทียบกับฝน 07:00–07:00 ห้ามคูณ rain rate เรดาร์หนึ่งภาพให้กลายเป็นฝนสะสมชั่วโมง ต้องมีการรวมตามเวลาและ QC แยก
- ล็อกพยากรณ์ที่เผยแพร่ก่อนช่วงเป้าหมาย และ input ต้องพร้อมก่อนเผยแพร่ แบ่ง lead 0–6, 6–24, 24–48, 48–72 ชม. และวัน 4–7 แยกกัน “วันนี้เหลือกี่ชั่วโมง” ต้องบันทึกจริง ไม่เรียกผลช่วงสั้นกว่าวันว่า daily forecast เต็มวัน
- แยกตอนนี้กับอนาคต; ถ้าพื้นที่น้ำท่วมอยู่แล้วตั้งแต่เวลาออกผล ให้เป็น ongoing/persistence ไม่ใช่การทำนายเริ่มท่วมสำเร็จ รวมรายงานซ้ำ/รายงานเหตุเดิมต่อเนื่องให้เป็นหนึ่งเหตุการณ์ ไม่เพิ่มคะแนนจาก refresh ทุก 15 นาที
- `unknown` แยกจาก wet/dry: ไม่มีรายงาน, ภาพไม่ชัด, สถานีไม่ส่ง หรือช่วงขาด ห้ามนับเป็นแห้ง แม้ท่วมจริงในพื้นที่ไม่มีผู้แจ้งก็อาจไม่อยู่ในชุดตรวจ รายงาน capture rate ต่อเหตุที่ตรวจยืนยันได้พร้อมข้อจำกัดนี้
- สรุประดับจังหวัด: ตรวจแยกการกระจายระดับหนัก/หนักมากและสัดส่วนเซลล์ที่มีข้อมูล ห้ามใช้ค่าสูงสุดจุดเดียวสรุปพื้นที่ส่วนใหญ่ ไม่อนุมานคำว่า “เกือบทั้งจังหวัด” จากสถานีวัดฝนหนึ่งแห่ง
- แบ่งชุดพัฒนา/ทดสอบตามเวลาและเหตุพายุทั้งเหตุ ไม่สุ่มชั่วโมงติดกันไปคนละชุด ล็อกกฎก่อนทดสอบ เปรียบเทียบกับ persistence และกฎฝนอย่างเดียวบนชุดคู่เดียวกัน Climatology ใช้เมื่อมีประวัติที่พอและถูกสิทธิ์ ไม่ถือว่า median หลายโมเดลแม่นกว่าโดยไม่ทดสอบ

## 4. คะแนนและเกณฑ์ตัดสิน

สำหรับคู่ฝนที่ครบ: `MAE = mean(abs(forecast − observed))`, bias ใช้ `forecast − observed`; รายงานหน่วย มม. และจำนวนคู่ แยกเกณฑ์ 1/10/35.1/90.1 มม. **เฉพาะหน้าต่าง 24 ชม.** และ 35 มม./ชม. เป็นเกณฑ์ทดลองของเว็บสำหรับหน้าต่างชั่วโมง แยกคู่ไม่ทราบ/ขาด/หลุด QC ทุกครั้ง

ให้ H = ถูกและเกิด, M = พลาดเหตุ, F = เตือนแต่มีหลักฐานว่าไม่เกิด, C = ไม่เตือนและยืนยันไม่เกิด: POD = H/(H+M), FAR = F/(H+F), CSI = H/(H+M+F). FAR ตรงนี้คือ **false alarm ratio**; ไม่ใช่ false alarm rate = F/(F+C). ตัวหารศูนย์แสดง “ประเมินไม่ได้” ไม่รายงาน 100% เพราะไม่มีเหตุ หากมีแต่ positive reports จะยังคำนวณ FAR/CSI ที่น่าเชื่อถือไม่ได้ ให้แสดง matched/unknown แทน

กรอบคะแนนและข้อควรระวัง point-to-grid อ้างอิง [ECMWF: high-density precipitation verification](https://www.ecmwf.int/en/newsletter/147/meteorology/use-high-density-observations-precipitation-verification), [high-resolution verification](https://www.ecmwf.int/en/about/media-centre/science-blog/2023/verifying-high-resolution-forecasts) และ [verification statistics](https://www.ecmwf.int/sites/default/files/elibrary/2010/11920-verification-statistics-and-evaluations-ecmwf-forecasts-2009-2010.pdf). ถ้ามี probability ของเหตุที่นิยามตรงกันจึงเพิ่ม Brier/reliability; คะแนน v0/สัดส่วนเซลล์เปียกไม่ใช่ probability น้ำท่วม

เสนอรอบแรก 30 วันเป็น **การตรวจความพร้อมข้อมูล** ก่อน จากนั้นประเมินเป็นเหตุฝน/พายุอิสระและสถานี: รายงาน coverage, จำนวนเหตุจริง, ช่วงความไม่แน่นอนด้วยการสุ่มซ้ำเป็นเหตุ/วัน (ไม่สุ่มพิกเซลหรือชั่วโมงที่สัมพันธ์กัน), lead time และแยกแต่ละพื้นที่นำร่อง ไม่ใช้จำนวนวันที่เก็บครบเป็นหลักฐานว่าแม่น ไม่ยกเป็นกฎ v1 จนเทียบ baseline บนช่วงที่กันไว้แล้วและไม่มีการลด missed events โดยแลกกับ false alarms ที่ไม่ได้เปิดเผย

## 5. เทสต์และของที่ต้องส่งกลับ

`tests/consumer/evaluation.ts` เป็น reference scorer สำหรับคู่ฝนที่จัดช่วงและผ่าน QC แล้ว ไม่อ่านข้อมูลสดและไม่ถูกนำไปใช้ในเว็บ; `evaluation.test.ts` ตรวจตาราง H/M/F/C ที่คำนวณมือ, null≠0, ตัวหารศูนย์, ค่าขอบ, leakage และคู่ซ้ำ เทสต์นี้ยังไม่ตรวจการจับคู่พื้นที่/ช่วง/QC ซึ่งต้องเพิ่มเมื่อมี archive ตัวอย่างจริง

Claude ส่งกลับ: ตัวอย่าง archive หนึ่งรอบ/หนึ่งรุ่นพยากรณ์/หนึ่งเหตุการณ์ (ไม่มีข้อมูลส่วนตัวหรือ key), ตาราง field และเวลาพร้อมจริง, งบดิสก์/retention, แผนที่ station→cell พร้อมระยะและขอบเขต, รายงาน coverage หนึ่งสัปดาห์ เมื่อครบแล้ว Codex เขียน integration tests ของการจับคู่ รวมรายงานมาช้า หน้าต่างข้ามเที่ยงคืน เวลา 07:00 และรุ่นข้อมูลแก้ย้อนหลัง ก่อนเริ่มคำนวณคะแนนจริง
