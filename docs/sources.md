> กติกา: ก่อนดึงข้อมูลจากแหล่งใหม่ต้องเพิ่มแถวในไฟล์นี้ก่อน และชั้นข้อมูลที่ `license` ยังเป็น `unknown` ต้องไม่แสดงสาธารณะ (ยกเว้นแสดงลิงก์ไปหน้าของเจ้าของ) · ขอข้อมูลเฉพาะผ่านช่องทางที่หน่วยงานเปิดรับจริง ไม่ส่งจดหมายขอทั่วไป (D27)
> โปรเจกต์นี้ **ไม่ใช่เชิงพาณิชย์และงบเป็นศูนย์** (D12) จึงใช้ข้อมูลที่เป็น non-commercial ได้ แต่ต้องไม่มีค่าใช้จ่าย

## ความหมายของคอลัมน์
- **access**: `public` = เรียกได้โดยไม่ต้องมี key · `key` = ต้องสมัคร (ฟรี) · `waitlist` = ต้องรอคิว · `permission` = ต้องขออนุญาตเจ้าของ · `unknown` = ยังไม่รู้วิธีเข้าถึง
- **license**: `ok` = เงื่อนไขชัดและใช้ได้ (ดูหมายเหตุเรื่องเครดิต) · `nc-ok` = จำกัด non-commercial ซึ่งเราใช้ได้ · `unknown` = ต้องตรวจหรือขออนุญาตก่อนเผยแพร่ · `restricted` = ห้ามใช้ตามที่ต้องการ
- **coverage**: `national` · `pilot` (กทม. และปริมณฑล) · `partial` · `global`
- **verified**: วันที่และวิธีตรวจ (`api` = เรียกจริง · `docs` = อ่านเอกสาร)

## 9. วิธีใช้ TMD NWP API และรายการ TMD API (อ่านคู่มือเมื่อ 2026-09-25)
**TMD NWP API** (`https://data.tmd.go.th/nwpapi/v1/...` คู่มือ `data.tmd.go.th/nwpapi/doc`)
- ยืนยันตัวด้วย header `authorization: Bearer <token>` และเลือกรูปแบบด้วย `accept` (JSON, XML, RDF, CSV) · ใช้ https เท่านั้น
- ข้อผิดพลาด: 401 token ผิดหรือหมดอายุ, 404 ไม่พบชื่อสถานที่, 422 request ไม่ถูกต้อง, 429 เกินเพดาน · เพดาน 60 request/นาที และ 100,000 datapoints/ชม. (ดูได้จาก header `X-RateLimit-Remaining` และ `X-Datapoint-Remaining`)
- **รายชั่วโมง** (`forecast/hourly/...`): โดเมน 2 กม. สูงสุด 48 ชม.; ขอตามพิกัด (`at?lat=&lon=`), ตามชื่อจังหวัด/อำเภอ/ตำบลภาษาไทย (`subarea=1` แนบพื้นที่ย่อยหนึ่งระดับ เช่น อำเภอ → ทุกตำบล) หรือตามภาค; พารามิเตอร์ `date`, `hour` (เวลาไทย), `duration` (≤ 48), `fields`
- ตัวแปรรายชั่วโมง: `tc`, `rh`, `slp`, `rain` (มม./ชม.), `ws10m`, `wd10m`, ลมที่ 925–200 hPa, `cloudlow`/`cloudmed`/`cloudhigh`, `cond` (1–12 เช่น 5 ฝนเล็กน้อย, 7 ฝนหนัก, 8 ฝนฟ้าคะนอง)
- **รายวัน** (`forecast/daily/...`): โดเมน 18 และ 27 กม. สูงสุด 126 วัน (`rain` = ฝนรวม 24 ชม., `tc_max`, `tc_min` ฯลฯ)
- **รายพื้นที่** (`forecast/area/...`): ต้องระบุ `domain` คือ 0 = 27 กม. ราย 6 ชม. 126 วัน · 1 = 18 กม. ราย 3 ชม. 10 วัน · 2 = 6 กม. รายชั่วโมง 72 ชม. · 3 = 2 กม. รายชั่วโมง 48 ชม.; ขอเป็นกรอบสี่เหลี่ยม ชื่อสถานที่ ภาค หรือลุ่มน้ำ และใช้ datapoint มาก
- endpoint “ตรวจสอบข้อมูล” (ช่วงข้อมูลที่มี) ไม่นับ datapoint → ใช้ตรวจว่ามีรอบโมเดลใหม่ก่อนดึงจริง
- รายชื่อสถานที่ของ NWP มี 77 จังหวัด 927 อำเภอ 7,416 ตำบล; พื้นที่นำร่องมี 79 อำเภอ/เขต และ 468 ตำบล/แขวง (กทม. 50/160, สมุทรปราการ 6/50, นนทบุรี 6/52, ปทุมธานี 7/60 รวมคลองหนึ่ง–คลองเจ็ดของคลองหลวง, นครปฐม 7/106, สมุทรสาคร 3/40) · แขวงของ กทม. เป็นชุดเก่า (ปัจจุบัน 180 แขวง) → แขวงที่ไม่มีชื่อในรายชื่อให้ขอตามพิกัดศูนย์กลาง ซึ่งได้ค่าพยากรณ์ที่จุด (point value) ต้องติดป้ายเช่นนั้น และต้องมี crosswalk ระหว่างรายชื่อเก่าของ NWP กับขอบเขตตำบลปัจจุบัน พร้อมบันทึก query point ที่ใช้จริง
- งบต่อรอบโดยประมาณ: 468–488 พื้นที่ × 48 ชม. × 3 ตัวแปร ≈ 67,000–70,000 datapoints (< 100,000/ชม.) และประมาณ 79 request ถ้าขอรายอำเภอด้วย `subarea=1` → ดึงเฉพาะเมื่อมีรอบโมเดลใหม่ ไม่ดึงทุก 15 นาที · นับรวมพิกัดทดแทนและ retry และอ่านงบจริงจาก header ก่อนเริ่ม (design ข้อ 4.3)

### 12.2 ลำดับที่แนะนำสำหรับ fontokmai

1. **ตลิ่งและเกณฑ์รายสถานี**: ตรวจจากบริการ DXS ที่อนุมัติแล้วว่ามี metadata เหล่านี้หรือช่องทางส่งออกที่ให้สิทธิ์หรือไม่ โค้ด/fixture ปัจจุบันยังไม่มี แต่ fixture เป็นข้อมูลสังเคราะห์ จึงใช้ยืนยันว่า DXS ทุกบริการไม่มีไม่ได้ จับคู่ด้วยรหัสสถานีและฝั่งใน/นอก รวมทั้งตรวจหน่วยและระดับอ้างอิงตรงกันก่อนใช้ คำนวณระยะเหลือถึงตลิ่งแต่ละฝั่ง (`ระดับตลิ่ง − ระดับน้ำ`) แสดงเกณฑ์เตือนแยกจากการเกินตลิ่ง
2. **ประวัติระดับน้ำและอัตราการไหล**: ถ้าได้ข้อมูลต่อเนื่องที่มีสิทธิ์ ใช้ดูการเพิ่ม/ลดและประกอบฝนที่วัด/พยากรณ์ ป้ายสูงสุดวันนี้เทียบเมื่อวานเพียงสองค่าไม่พอคำนวณความเร็วเพิ่มของน้ำหรือเวลาล้น ไม่แปลงจำนวนปั๊มเป็นกำลังระบายเมื่อไม่รู้กำลังและสถานะเดินเครื่อง
3. **น้ำขึ้นและโครงข่ายระบายน้ำ**: ใช้ประกอบโอกาสระบายติดขัดเมื่อรู้ตำแหน่ง/ฐานระดับของสถานีน้ำขึ้น ความเชื่อมโยงคลอง ประตูและปั๊ม ไม่บวกตัวเลขน้ำขึ้นเข้าระดับคลองทุกแห่งโดยตรง และไม่ถือว่าลูกศรบนแผนผังคือการไหลสดที่ยืนยันแล้ว ต้องตรวจความหมายจากต้นทาง
4. เริ่มกับสถานีที่ข้อมูลครบในพื้นที่นำร่อง การสรุปเสี่ยงเป็น “ทดลอง” บอกหลักฐานและเวลา; ระดับจุดเดียวกับภาพผังยังไม่พอคำนวณปริมาตรน้ำที่จะทะลักหรือขอบเขตท่วม ต้องมีหน้าตัดคลอง/ภูมิประเทศ/โครงสร้างควบคุมและทดสอบย้อนหลังตาม design 7.6–7.10

### 12.3 สิทธิ์และช่องทาง

หน้าที่ตรวจมีเครดิต กทม. แต่ยังไม่พบ license ส่งต่อข้อมูลหรือเอกสาร public API/ระบบสมัครสำหรับนำฟีด Flood69 ไปใช้ การที่เว็บหนึ่งเผยแพร่ข้อมูลไม่ใช่หลักฐานว่าให้เราทำสำเนาผ่านตัวกลางได้ และสิทธิ์ DXS เดิมไม่ได้พิสูจน์ว่าครอบคลุมภาพ/metadata KlongMap ทุกชุด คง `unknown` ไว้ ไม่ตัดสินว่าเจ้าของเว็บมีหรือไม่มีสิทธิ์

ระหว่างนี้ใช้เป็นแหล่งอ้างอิง/ลิงก์ออกและหลักฐานว่ามีข้อมูลประเภทนี้ หากพบชุดเปิดหรือระบบสมัครจริงจึงบันทึก C1 ให้ผู้ใช้เลือกตาม D27 ไม่มีการส่งคำขอ สมัครบัญชี อ่าน token ใน JavaScript เรียก endpoint ภายใน หรือคัดลอกภาพผังมาใช้ในรอบนี้ ไม่ได้เพิ่มข้อมูลเข้า pipeline หรือยืนยันความแม่นของการคำนวณใหม่


## 13. ตรวจที่มาเกณฑ์ฝนที่สรุปอ้างชื่อ สสน. (Codex 2026-09-28)

**ผล: ยังยืนยันไม่ได้** ว่า 35 มม./1 ชม., 95 มม./24 ชม. และ 150 มม./3 วัน เป็นเกณฑ์ปัจจุบันของ สสน. ที่ให้ใช้แบบเดียวกันทั่วประเทศหรือกับพยากรณ์ล่วงหน้า ไม่ใช่ข้อสรุปว่า สสน. ไม่เคยใช้ตัวเลขนี้ เอกสาร design 7.5 อ้าง “เขตเตือนภัย 06” แต่ยังไม่มี URL/field/version ที่ตรวจย้อนกลับได้ และกำชับให้ตรวจซ้ำก่อนใช้

แหล่งทางการที่ตรวจ:

- [คู่มือ ThaiWater 2017](https://tiwrm.hii.or.th/v3/uploads/manual_2017.pdf) หน้าเลขพิมพ์ 12–14 (PDF 17–19): หน้า 12 อธิบายฝน **ย้อนหลัง 24 ชั่วโมง** และเกณฑ์เบา 0.1–10, ปานกลาง 10.1–35, หนัก 35.1–90, หนักมากตั้งแต่ 90.1 มม.; หน้า 13 เป็นการอ่านเรดาร์; หน้า 14 อธิบายพยากรณ์ WRF และช่วงสะสม ไม่พบตารางยืนยัน 35/95/150 ในส่วนที่ตรวจ ต้องไม่สลับเกณฑ์ความหนักกับเกณฑ์เตือนน้ำท่วม
- [บันทึกน้ำท่วมตุลาคม 2017](https://tiwrm.hii.or.th/current/2017/floodOct2017/body.html) มีรายการส่งเตือนตามปริมาณฝน/ช่วงสะสมในอดีต แต่ค่าที่เคยส่งเตือนไม่พอยืนยัน boundary, AND/OR, เขต 06 หรือเวอร์ชันปัจจุบัน
- [หน้า ThaiWater](https://www.thaiwater.net/) เป็นเว็บ JavaScript; การอ่านผ่าน web text ครั้งนี้ไม่แสดงตารางเกณฑ์ จึงไม่ถือว่าตรวจทุกหน้าหรือทุกระบบครบ ไม่เรียกช่องทางหลังบ้านหรือใช้ token จาก JavaScript เพื่อหาตาราง
- ค้นข้อความตรงและคำ “เกณฑ์/เฝ้าระวัง/เขตเตือนภัย 06” ในโดเมนทางการ hii.or.th/tiwrm.hii.or.th/thaiwater.net ยังไม่มีเอกสารที่ยืนยันทั้งสามค่าและขอบเขตการนำไปใช้

**M23 — ขอให้ Claude เปลี่ยนถ้อยคำอ้างอิง** ใน `overview_build.py`, หน้า method, แบบระบบ/คำอธิบายและเทสต์ที่เกี่ยวข้อง เป็น “เกณฑ์ทดลองของเว็บ” ก่อน โดยยังไม่เปลี่ยนตัวเลขเงียบๆ หรืออ้างว่าเทียบเท่าประกาศ สสน. เกณฑ์แบ่งความหนักฝนรายวันของกรมอุตุฯ ที่มีหลักฐานคงแยกได้ ส่วนฝนสะสม “3 วัน” ในโค้ดเป็นชั่วโมงที่เหลือวันนี้ + 2 วันถัดไป ต้องระบุช่วงให้ตรง และ rain rate จากเรดาร์ไม่เท่าฝนสะสม 1 ชั่วโมง

เกณฑ์ปิดเรื่องที่มา: มีหน้า/เอกสารทางการที่ชี้ field หรือหน้าตารางได้ พร้อมวัน/รุ่น, พื้นที่, หน่วย/หน้าต่างสะสม, observed หรือ forecast, เครื่องหมาย ≥/>, AND/OR และหลักฐานสิทธิ์หากนำข้อมูล API มาใช้; หรือถอดการอ้างชื่อ สสน. จากกฎที่ยังไม่ยืนยันทั้งหมดและคงป้ายทดลอง/ยังไม่ได้ตรวจความแม่น ไม่ต้องให้ผู้ใช้ส่งคำขอทั่วไปตาม D27

## 14. ตัวอย่าง CCTV และเส้นทางน้ำที่ผู้ใช้ส่ง — 2026-09-30 (Codex)

### 14.1 cctv.maholan.net: วิธีแสดงภาพไม่ใช่หลักฐานสิทธิ์นำภาพมาใช้ต่อ

ตรวจ [หน้าเว็บสาธารณะ](https://cctv.maholan.net/) ด้วยเบราว์เซอร์: การ์ดรังสิต 200 ปี, เทศบาลเมืองปทุมธานี และคลองรังสิตประยูรศักดิ์ (สะพานแดง) ใช้ `<img>` ที่รับภาพจากเส้นทาง `/api/snap/...` บนโดเมนของเว็บเอง ภาพตัวอย่างโหลดได้ การกดรังสิต 200 ปีเปิดหน้าขยายที่มี `<img>` จาก `/api/stream/...` และขึ้น “กำลังต่อสตรีมสด…” ขณะตรวจ จึงยืนยันได้ว่าแสดงภาพผ่านบริการของเว็บรวมกล้อง แต่ **ยังไม่ยืนยันว่าถ่ายทอดสดต่อเนื่องสำเร็จหรือภาพทุกตัวใหม่จริง**; หลายการ์ดขึ้น “ดูเวลาบนภาพ” และบางตัวออฟไลน์

นี่อธิบายทางเทคนิคว่าทำหน้ารวมภาพได้ ไม่ใช่ข้อสรุปว่าเจ้าของเปิด API ให้เว็บอื่นใช้ หรือตัวเว็บได้รับ/ไม่ได้รับอนุญาต ไม่ได้ตรวจระบบภายในหรือดึง stream URL/credential ของกล้องมาใช้ต่อ รอบนี้ไม่มีหลักฐานสิทธิ์ภาพรายกล้องเพิ่ม จึง **ไม่ลงทะเบียนเว็บรวมนี้เป็นแหล่งภาพของ pipeline** และไม่ใช้ proxy เพื่อเลี่ยงข้อจำกัดเจ้าของ (D27/D32)

ข้อเสนอให้ Claude: ตรวจกล้องพื้นที่นำร่องทีละตัว เริ่ม candidate ช่องทางเทศบาลปากเกร็ดตาม §11.3; ใช้ player/embed ที่เจ้าของเปิดให้ หรือภาพนิ่งเมื่อยืนยันสิทธิ์แล้วเท่านั้น แสดงเวลาภาพแยกจากเวลาที่เว็บดึง, ไม่ติดป้าย “สด” จากการดาวน์โหลดสำเร็จอย่างเดียว, กดแล้วค่อยโหลด และมีลิงก์ต้นทางเมื่อเล่นไม่ได้ สถานะปัจจุบันของ fontokmai ที่ใช้ลิงก์ออกเป็นขอบเขต implementation/ทะเบียน ไม่ใช่ข้อจำกัดว่าเว็บประเภทนี้ฝังกล้องไม่ได้เลย

### 14.2 น้ำคลอง: ใช้แนวคิดได้ แต่ต้องแยกแนวแม่น้ำกับกระแสน้ำจริง

ตรวจ [แผนที่น้ำคลอง](https://namkhlong.horjorkor.com/#map) และ [แหล่งข้อมูลและวิธีการ](https://namkhlong.horjorkor.com/#sources) ผ่านหน้าเว็บ: ระบุโครงข่ายจาก OpenStreetMap + BMA GIS, สถานีสูบจาก data.bangkok.go.th, ข้อมูลวัดผ่าน ThaiWater และ DDS; สีคลองใช้สถานีบนคลองนั้นในรัศมี 3 กม. ลูกศรจำกัดช่วงแม่น้ำและ 500 ม. ก่อนสถานีสูบ หน้าข้อจำกัดระบุว่าไม่มีสถานะเดินเครื่อง/เปิดประตูสาธารณะ และคลองที่ไม่ทราบทิศไม่แสดงลูกศร ขณะตรวจแสดงระดับเจ้าพระยาสองสถานีคือสะพานเดชาติวงศ์กับสะพานกรุงเทพเป็นเหตุผลของทิศไปทะเล

**ขอบเขตหลักฐาน**: ข้างต้นเป็นวิธีที่เว็บไซต์แจ้ง ไม่ใช่การรับรองความถูกต้องหรือใบอนุญาตให้คัดลอกโค้ด/ข้อมูลของเว็บไซต์ และไม่ได้ยืนยันสิทธิ์ API ThaiWater/BMA ใหม่ ข้อความเรื่องไม่มีข้อมูลการเดินเครื่องของเว็บไซต์นั้นไม่เปลี่ยนข้อเท็จจริงว่า fontokmai มีจำนวนเครื่องเดินบางสถานีผ่าน DXS ที่ผู้ใช้ได้รับแล้ว

**เสนอทำได้ด้วยแหล่งที่มี**: เพิ่ม GeoJSON แนวแม่น้ำจาก [HydroRIVERS](https://www.hydrosheds.org/products/hydrorivers) ซึ่งลงทะเบียนและให้เครดิตใน §5 แล้ว ใช้เป็น “เส้นทางท้ายน้ำตามโครงข่าย” เมื่อเลือกเขื่อน ปัจจุบัน `dam_downstream.json` เก็บเพียงอำเภอ/ระยะและจุดสิ้นสุด ไม่ได้เก็บเส้น จึงต้องให้ Claude ส่งสัญญา geometry เพิ่ม; ห้ามลากเส้นเชื่อมจุดกลางอำเภอแล้วเรียกแนวแม่น้ำ และ HydroRIVERS ไม่แทนคลองย่อยทั้งหมดในรังสิต

**ยังไม่ควรอ้าง**: ตำแหน่งปั๊มอย่างเดียวไม่พิสูจน์ว่ากำลังสูบเข้าทางใด, ระดับน้ำสองสถานีไกลกันไม่เพียงพอให้รับรองกระแสน้ำทุกช่วงหรือการไหลกลับจากน้ำหนุน และระยะทางหารความเร็วสมมติไม่ใช่เวลาน้ำหลากถึงบ้าน [USGS: การคำนวณ discharge ในพื้นที่น้ำขึ้นลง](https://www.usgs.gov/publications/computation-discharge-using-index-velocity-method-tidally-affected-areas) ใช้ทั้งระดับ/หน้าตัดและความเร็วที่วัด; [คู่มือ index velocity](https://pubs.usgs.gov/tm/3a23/) อธิบายการสอบเทียบ ความไม่แน่นอน และแยก velocity/area การแสดง “ทิศทางขณะนี้” ต้องมีหลักฐานของช่วงนั้น เวลา/datum หน่วยตรงกันและ freshness หรือแบบจำลองที่ตรวจแล้ว; ยังไม่แสดงเวลาถึง ขอบเขตท่วม หรือความปลอดภัยจากเส้นเพียงอย่างเดียว

ไม่มีการสมัคร ติดต่อเจ้าของ คัดลอกภาพ/ข้อมูลจำนวนมาก หรือแก้ pipeline/เว็บในรอบตรวจนี้ รายละเอียด UI และเกณฑ์รับงานฝากไว้ใน `private/handoffs/2026-09-30-codex-review.md`

### 15.3 ข้อจำกัดของแบบและเกณฑ์ความจุ

[GloFAS FAQ](https://confluence.ecmwf.int/spaces/CEMS/pages/315563119/6%2BFAQ%2Bin%2BGloFAS) ระบุว่าแบบจำลองมีอ่างขนาดใหญ่และคำนวณการระบายจากระดับเก็บกัก แต่ไม่ใช้กฎปฏิบัติการของแต่ละพื้นที่จริง การเอาการระบายของเขื่อนมาบวกบน Q ของ GloFAS หรือสถานีท้ายน้ำทั้งก้อนจึงอาจนับน้ำซ้ำ ต้องรู้ฐานการระบายที่โมเดลใช้หรือคำนวณโครงข่ายแบบแบ่งพื้นที่เอง รวมผลของน้ำผัน/น้ำเก็บและความหน่วงด้วย

[HEC-HMS: ข้อจำกัดการ routing](https://www.hec.usace.army.mil/confluence/hmsdocs/hmstrm/channel-flow/applicability-and-limitations-of-channel-routing-models) ระบุข้อจำกัด Muskingum กับน้ำหนุน/โครงสร้างควบคุม; [HEC-RAS: ประตู](https://www.hec.usace.army.mil/confluence/rasdocs/rasum/6.3/entering-and-editing-geometric-data/inline-structures-dams-weirs-and-gated-spillways) แยก geometry กับการเปิดตามเวลา จึงไม่เลือกวิธีไหลทางเดียวแบบง่ายแทนทุกคลองรังสิต อ้างวิธีเพื่อออกแบบ ยังไม่ได้ติดตั้งหรือเลือก license ของ solver ใด

ความจุอ่าง (ล้าน ลบ.ม.), ความสามารถระบาย (ลบ.ม./วินาที) และระดับตลิ่ง (ม.ตาม datum) เป็นคนละค่า ข้อมูลตลิ่ง/เกณฑ์ต้องระบุฝั่ง/ช่วง/วันที่/ฐานระดับและเงื่อนไขท้ายน้ำ แผนที่ของเราแสดงสีแนวโน้มน้ำจากโมเดลอยู่แล้ว แต่สีแดงนี้ไม่พิสูจน์ว่าน้ำล้นตลิ่ง

รอบนี้อ่านเอกสาร/ทะเบียนที่เปิดตามสิทธิ์ ตรวจไฟล์ของเรา และจัดแผน ไม่มีการสมัคร ติดต่อหน่วยงาน ดึงข้อมูลหลังบ้านหรือเพิ่มการคำนวณในเว็บจริง


### 15.4 เริ่มใช้ ensemble ระยะแรก (2026-10-03)
